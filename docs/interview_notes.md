# 面试讲解笔记

## 1. 项目一句话介绍

这是一个面向工业设备运维场景的知识库 RAG 与故障诊断 Agent 系统，使用 FastAPI、LangChain、Chroma、MySQL 和 Function Calling，把设备文档、历史报警、维修记录结合起来，为现场故障排查生成可追溯的诊断建议和 Markdown 报告。

## 2. 项目背景

制造业设备运维场景中，现场工程师遇到设备报警或异常时，通常需要同时查说明书、SOP、历史报警、维修工单和设备台账。传统方式依赖人工翻文档和经验判断，效率比较低，也不容易追溯依据。

这个项目模拟了这样的业务场景：先用 RAG 解决非结构化设备文档检索问题，再用 MySQL 保存设备、报警、维修等结构化业务数据，随后通过 Function Calling 把这些能力封装成工具，最后编排成故障诊断流程并生成 Markdown 报告。

项目的重点不是做一个泛聊天机器人，而是展示一个比较完整的大模型应用后端链路：知识库、业务数据、工具调用、诊断流程、报告保存和历史查询。

## 3. 我在项目中做了什么

我在这个项目中主要完成了后端核心链路的设计和实现。

首先，我搭建了基于 FastAPI 的接口服务，支持文档上传、知识库问答、设备查询、工具调用问答和诊断报告生成。其次，我使用 LangChain 和 Chroma 实现了文档解析、切块、Embedding 和相似度检索，并通过相似度阈值控制知识库引用的可靠性。

在业务数据层，我用 SQLAlchemy 建模了设备、报警、维修、聊天历史和诊断报告等表，并通过初始化脚本写入可演示的样例数据。在工具调用层，我把知识库检索、设备查询、报警查询和维修查询封装成 Function Calling 可调用的工具，并返回 `tool_calls` 记录调用过程。

最后，我在阶段四实现了故障诊断流程编排：系统会结合知识库、设备台账、历史报警和维修记录生成结构化诊断结论，再整理成 Markdown 报告，并保存到 MySQL，支持后续按报告编号或会话编号查询。

整个项目是一个模拟工业设备运维场景的学习型项目，没有夸大成生产级系统，但覆盖了 RAG 应用开发中比较关键的工程环节。

## 4. 项目技术架构怎么讲

### FastAPI 接口层

FastAPI 负责对外提供接口和 Swagger 测试入口。项目中主要接口包括普通 RAG 问答、文档上传、设备查询、工具调用问答、故障诊断、诊断报告生成和报告历史查询。使用 FastAPI 的好处是接口结构清晰，方便本地调试和面试演示。

### RAG 知识库层

RAG 层负责处理非结构化设备文档。文档会先解析成文本，再切成 chunk，然后用智谱 Embedding API 生成向量并写入 Chroma。用户提问时，系统从 Chroma 中检索相关片段，只有高于阈值的片段才作为可信 sources 返回，避免知识库外问题强行编造来源。

### MySQL 业务数据层

MySQL 层保存结构化业务数据，包括设备台账、报警记录、维修记录、聊天历史和诊断报告。相比只做 RAG 文档问答，引入 MySQL 后可以让系统回答更接近真实运维场景的问题，例如“这台设备最近有哪些报警”和“历史维修怎么处理过”。

### Function Calling 工具层

工具层把知识库检索和数据库查询封装成工具函数，包括 `search_knowledge_base`、`query_device_info`、`query_alarm_records` 和 `query_maintenance_records`。系统会返回 `tool_calls`，记录调用了什么工具、传了什么参数、是否成功和结果摘要，方便调试和解释。

### 诊断报告层

诊断报告层在工具能力基础上做流程编排。系统先整合 `evidence`，再生成结构化诊断结论，最后输出 Markdown 报告。报告中明确区分知识库依据、设备基础信息、历史报警和历史维修记录，并保存到 MySQL 供后续查询。

## 5. 项目难点怎么讲

### Chat 模型和 Embedding 模型解耦

项目一开始就把 Chat 模型和 Embedding 模型分开配置。DeepSeek 主要用于文本生成，智谱 Embedding 用于向量化。这样设计的原因是聊天模型不一定适合作为 Embedding 服务，工程上应该选择合适的模型做合适的任务。

### 知识库外问题防止编造引用

RAG 项目容易出现一个问题：知识库没有依据时，模型仍然生成看起来很像的答案。项目中通过相似度阈值过滤低可信检索结果，如果没有可靠 sources，就返回空数组并明确提示无可靠依据，避免伪造引用来源。

### RAG 和业务数据库结合

工业运维场景既有说明书、SOP 这类非结构化文档，也有设备台账、报警记录、维修工单这类结构化数据。项目把两类数据结合起来，让诊断结果既有文档依据，也能参考历史业务记录。

### 工具调用过程可观测

Function Calling 不是只追求最终回答，还要能看到工具调用过程。项目返回并保存 `tool_calls`，可以观察系统调用了哪些工具、输入参数是什么、是否执行成功。这对调试、验收和面试讲解都很有帮助。

### 报告生成和历史追溯

阶段四把一次问答升级为一份可保存的诊断报告。报告不仅包含最终结论，还包含证据和工具调用记录，后续可以按 `report_id` 或 `session_id` 查询。这样比普通聊天记录更适合工业运维场景中的问题追溯。

## 6. 面试官可能问的问题和回答

### 1. RAG 是什么？

RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。它的核心思想是先从外部知识库中检索和问题相关的内容，再把这些内容作为上下文交给大模型生成回答。这样可以让模型回答基于项目自己的知识，而不是只依赖模型预训练记忆。

### 2. Embedding 是什么？

Embedding 是把文本转换成向量的过程。向量可以表达文本语义，系统可以通过向量相似度判断用户问题和文档片段是否相关。在这个项目中，设备说明书、SOP、维修案例会被切块并生成向量，用户问题也会生成向量，然后在 Chroma 中做相似度检索。

### 3. 为什么用 Chroma？

Chroma 是一个适合本地开发和演示的向量数据库，部署成本低，和 LangChain 集成方便，也支持持久化保存向量。对这个求职展示项目来说，它能比较快地跑通知识库入库和检索闭环。如果是真实生产环境，可以根据数据规模和运维要求换成 Milvus、pgvector 或 Elasticsearch 向量检索方案。

### 4. 为什么用 MySQL？

MySQL 用来保存结构化业务数据，例如设备台账、报警记录、维修记录、聊天历史和诊断报告。RAG 更适合处理文档知识，但企业系统中还有很多结构化数据，这些数据用关系型数据库管理更自然，也更方便按设备编号、会话编号或报告编号查询。

### 5. 为什么需要 Function Calling？

普通 RAG 主要是检索文档并生成回答，但工业运维问题往往需要查设备信息、报警记录、维修记录等多个数据源。Function Calling 可以把这些查询封装成工具，让系统根据问题调用合适工具，再基于工具结果生成回答。这样比把所有逻辑塞进 prompt 更清晰，也更容易调试。

### 6. Function Calling 和普通 RAG 有什么区别？

普通 RAG 的核心是“检索文档片段 + 生成回答”。Function Calling 更像是让模型或系统具备调用外部函数的能力，比如查数据库、查报警、查维修记录。这个项目里两者是结合使用的：知识库检索本身也是一个工具，数据库查询也是工具。

### 7. tool_calls 有什么用？

`tool_calls` 记录系统调用了哪些工具、传入了什么参数、是否成功、结果摘要是什么。它的作用是增强可观测性。对开发来说方便调试；对验收来说可以证明系统确实查了知识库或数据库；对面试来说可以清楚展示 Function Calling 的执行过程。

### 8. 为什么要保存聊天历史？

保存聊天历史可以让一次问答不只是临时响应，而是可追溯的记录。用户可以按 `session_id` 回看之前问过什么、系统回答了什么、引用了哪些 sources、调用了哪些工具。这对设备运维场景中的问题复盘有价值。

### 9. 为什么要保存诊断报告？

诊断报告比普通回答更结构化，包含基本信息、故障现象、设备信息、知识库依据、报警记录、维修记录和综合结论。保存报告后，可以按 `report_id` 查询单份报告，也可以按 `session_id` 查询同一会话下的报告列表，方便后续展示和追溯。

### 10. 知识库外问题怎么处理？

项目中设置了相似度阈值。如果知识库检索结果低于阈值，就不把它当作可靠来源，`sources` 或 `knowledge_sources` 会返回空数组。报告中也会明确写“知识库未检索到高于阈值的可靠依据”。这样可以减少模型编造来源的问题。

### 11. DeepSeek 和智谱分别负责什么？

DeepSeek Chat API 负责文本生成，包括普通回答、工具结果总结、结构化诊断结论等。智谱 Embedding API 负责把文档片段和用户问题转换成向量。两者解耦后，每个模型只负责自己更适合的任务。

### 12. FastAPI 在项目中负责什么？

FastAPI 是后端接口层，负责接收请求、调用业务逻辑、返回响应，并自动生成 Swagger 文档。项目中所有核心能力，包括文档上传、RAG 问答、设备查询、Function Calling、诊断分析和报告查询，都是通过 FastAPI 接口暴露的。

### 13. SQLAlchemy 负责什么？

SQLAlchemy 负责 ORM 建模和数据库访问。项目中用它定义了 `devices`、`alarm_records`、`maintenance_records`、`chat_records`、`diagnosis_reports` 等表，并在 CRUD 层封装查询和保存逻辑，避免接口层直接写 SQL。

### 14. 项目如何扩展到真实企业？

如果扩展到真实企业，需要接入真实设备台账、报警系统、工单系统和权限体系；数据库迁移要使用 Alembic 这类生产级方案；向量库也可能换成更适合大规模部署的方案；同时要补充日志、监控、权限、审计和部署流程。当前项目是模拟场景，重点展示核心技术链路。

### 15. 项目目前有哪些不足？

当前项目还没有做前端、权限系统、生产级数据库迁移、复杂多轮 Agent、自动评测和线上部署。诊断流程是固定编排，不是完全自主规划型 Agent。这个选择是有意的，因为我希望先把 RAG、业务数据、工具调用和报告保存这些后端基础能力做扎实。

### 16. 后续如何优化？

后续可以增加 Streamlit 或前端页面展示；引入更完善的评测集验证回答质量；用 Alembic 管理数据库迁移；增加工具调用耗时和失败原因记录；引入更细粒度的权限和日志；如果诊断流程变复杂，再考虑 LangGraph 或工作流引擎。

### 17. 为什么没有直接用 LangGraph？

当前阶段的诊断流程比较明确：查设备、查知识库、查报警、查维修、整理证据、生成诊断、生成报告。这个流程用普通代码编排更清晰，也更容易验收。LangGraph 更适合复杂多节点、多轮状态流转的 Agent。项目没有为了追热点而强行引入复杂框架。

### 18. Agent 和 Function Calling 有什么区别？

Function Calling 更偏工具调用能力，也就是模型或系统能调用外部函数。Agent 更强调在目标驱动下进行规划、选择工具、执行、观察结果并继续决策。这个项目里阶段三实现了 Function Calling，阶段四做的是固定流程的诊断 Agent 雏形，还不是复杂多轮自主 Agent。

### 19. 如何保证回答可信？

项目主要通过三点提高可信度：第一，RAG 回答返回 sources，并用相似度阈值过滤低可信片段；第二，业务数据来自 MySQL 查询结果，不让模型编造设备、报警或维修记录；第三，诊断报告中保留 evidence 和 tool_calls，让依据和工具调用过程可以追溯。

### 20. 这个项目和你的控制工程背景有什么关系？

我的控制工程背景让我更熟悉设备、报警、故障排查和工业运维这类场景。这个项目不是单纯做通用聊天，而是把大模型技术放到设备运维问题中，模拟现场工程师如何结合说明书、报警记录和维修工单做排查。它体现了我从控制工程转向 AI 大模型应用开发时，对业务场景和工程实现的结合能力。

### 21. 为什么报告使用 Markdown？

Markdown 结构清晰、容易生成、容易在前端渲染，也适合保存到数据库。当前阶段只生成 Markdown 字符串，不做 PDF 或文件下载，是为了先把报告内容和历史追溯链路做稳定。后续如果需要展示或导出，可以在 Markdown 基础上继续扩展。

### 22. 如果设备编号不存在怎么办？

如果传入的 `device_code` 不存在，系统不会编造设备信息，也不会阻断诊断或报告生成。报告中会明确说明未查询到该设备编号对应的设备信息，保存时 `device_id` 为空。这样既保证功能可用，又避免生成假的业务数据。

### 23. 这个项目怎么体现工程能力？

它不是只写 prompt，而是拆成了接口层、RAG 层、数据库层、工具层、诊断层和文档测试。每个阶段都有明确验收目标和测试，接口响应结构也比较清晰。比如 `sources`、`evidence`、`tool_calls`、`report_id` 都是为了让系统可调试、可追溯、可展示。

### 24. 如果面试官问你最有收获的点是什么？

我会说最大的收获是理解了大模型应用不只是调用一个 Chat API，更重要的是把外部知识、业务数据和工程流程组织好。RAG 解决文档依据，数据库解决业务事实，Function Calling 解决工具调用，报告保存解决追溯。把这些环节串起来，才更接近真实企业应用。
